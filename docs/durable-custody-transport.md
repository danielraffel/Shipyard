# Durable cross-machine custody transport

Shipyard can reconcile its append-only custody inbox across machines without a
shared database, broker, model, or terminal session. The carrier is disabled by
default. When enabled, each daemon periodically runs one bounded background
reconciliation pass; an offline peer leaves the durable source record pending
for a later pass.

## State semantics

`shipyard work-ledger custody-status` reports exact persisted states:

- outgoing `pending` and `claimed` have not yet received destination custody;
- outgoing `accepted` means the destination committed the authenticated
  envelope before returning its receipt;
- incoming `received` has not been claimed by a consumer;
- incoming `processing` has an active, leased consumer claim;
- `processed` means the effect and its receipt were durably committed;
- `cancelled` and `superseded` are authenticated append/control outcomes.

There is intentionally no `read` state. SSH delivery, terminal visibility, or a
human viewing a record cannot prove that an agent read it. Corrections and
revocations append authenticated controls; they never overwrite the original
message and lose atomically to an already committed processing effect.

`shipyard --json work-ledger custody-inventory --message wm_<64hex>` queries
only the destination bound by the source ledger's exact active custody rebind.
`pending` and `claimed` return `uncertain` without contacting a host;
`custody_accepted` and `processed` may return `complete` or `partial` inventory;
cancelled, superseded, missing, malformed, or contradictory custody returns
`refused`. The request digest binds the complete source incarnation, target
machine/incarnation/route/adapter, active rebind epoch, authority, identity,
and transfer tuple. The receiver authenticates that tuple against its exact
inbox before invoking the immutable local inventory reader. Neither endpoint
opens the ledger writable for inventory.

Optional `--correlation-hints /owner-only/private.json` accepts only a bounded,
no-follow, owner-only object containing `linear_workspace_id`, canonical
`linear_root_uuid`, and `provider_repository_id`. These values are copied only
into the local rendered result. They are never sent over SSH, included in a
request digest, used to select a route, or treated as Shipyard authority.

The sender retains its source custody through the processed acknowledgement.
If either daemon restarts after destination acceptance but before source
acknowledgement, replay returns the same receipt and does not create a second
inbox item or effect. Processed acknowledgements are recorded in the receiver's
same protected WAL ledger so receiver restart also remains idempotent.

## Protected machine policy

Configuration belongs in the owner-private machine-global Shipyard config, not
a repository config. Omission or `enabled = false` has zero stewardship effect.
All identities and authority digests are opaque values generated by the custody
authority; labels such as hostnames are not trusted as identity.

### Setup and diagnosis

Provisioning is explicit and dry-run first. Prepare an owner-only TOML
manifest containing `schema_version = 1`,
`custody_transport.setup_contract_version = 1`, and the complete
`[custody_transport]` table below, then run:

The manifest's top-level `schema_version` describes the input envelope; the
`setup_contract_version` inside `[custody_transport]` describes the guarded
readiness contract. They are checked independently. A missing or unknown
contract marker is never interpreted as the new contract.

```bash
shipyard --json custody provision --input /owner/private/shipyard/custody/m3.toml
shipyard --json custody provision --input /owner/private/shipyard/custody/m3.toml --apply
shipyard --json custody doctor
shipyard --json custody disable --policy-digest <digest>
shipyard --json custody disable --policy-digest <digest> --apply
```

The first command does not write anything. `--apply` may only add an absent
policy to the canonical machine-global `config.toml`; an equivalent policy is
an idempotent no-op, while a different existing policy is refused. The write
is protected by Shipyard's writer-domain lease and an atomic replace, with a
fresh reread immediately before publication. The machine-global directory and
policy are owner-only (0700/0600), and the manifest itself must be a regular
owner-only file. No repository or checkout-local configuration is read.

The setup validator binds every opaque machine, incarnation, route, owner, and
authority digest exactly as supplied. It checks each peer's dedicated private
identity and `known_hosts` file without following symlinks, derives the public
key digest with `ssh-keygen -y`, and requires an exact match to
`ssh_auth_key_sha256`. Add the receiver paths to the policy for setup:

Peer keys are directional. `identity_file` plus
`outbound_identity_sha256` describe the local private key used when sending to
that peer. `inbound_public_key_file` plus `ssh_auth_key_sha256` describe the
peer's public key that must appear in this host's `authorized_keys`. These
values are intentionally separate; Shipyard never copies or derives one
direction from the other.

An enabled policy also carries three owner-attested readiness digests:
`destination_bootstrap_digest`, `native_publication_digest`, and
`profile_digest`. They are opaque fences for the exact external bootstrap,
native-publication authority, and private host profile. Shipyard requires all
three but does not create, copy, or infer any of them; a missing or malformed
digest keeps provisioning in a dry-run/refused state.

Each receipt file is owner-only (`0600`), bounded, regular, and contains
`schema_version`, `kind`, `machine_ref`, `incarnation_ref`, `route_ref`,
`authority_digest`, `destination_bootstrap_digest`, `profile_digest`,
`native_publication_digest`, and a `payload_digest` over that canonical payload.
Runtime policy loading verifies these bindings and the digest on every load, so
hand-written hex values or replayed receipts cannot enable the carrier.

Policies written before this setup contract have no marker. They remain
runtime-compatible for recovery, but `custody doctor` reports
`migration_required` and not-ready. To migrate, quiesce custody, run
`shipyard custody doctor` to capture the exact legacy policy digest, then run
`shipyard custody disable --policy-digest <legacy-digest> --apply` and provision
a marked manifest with the commands above. Do not edit the machine-global TOML
by hand; an unknown marker is always refused.

```toml
sshd_config_file = "/etc/ssh/sshd_config"
authorized_keys_file = "/owner/private/shipyard/custody/authorized_keys"
destination_bootstrap_digest = "<owner-attested sha256>"
native_publication_digest = "<owner-attested sha256>"
profile_digest = "<owner-attested sha256>"
receiver_program = "/owner/private/bin/shipyard"
destination_bootstrap_receipt_file = "/owner/private/shipyard/custody/destination-bootstrap.json"
native_publication_receipt_file = "/owner/private/shipyard/custody/native-publication.json"
profile_receipt_file = "/owner/private/shipyard/custody/profile.json"
```

The doctor verifies the effective include-expanded `sshd -T` output for
`ExposeAuthInfo yes`, the fixed `shipyard-custody-v1` subsystem (including the
full receiver argv), and an `AuthorizedKeysFile` that resolves to the exact
configured owner path. If `sshd -T` is unavailable, exits non-zero, or emits an
ambiguous contract, setup is refused; Shipyard never falls back to a partial
file scan. It then checks one authorized key for every configured peer. These
checks are read-only. Shipyard does **not** edit `sshd`, generate keys, install
`authorized_keys`, or infer a route from a hostname; those are privileged owner
operations covered by the host runbook.

This command is the supported Shipyard-side provisioner, not a complete
cross-host enrollment workflow. A GEN-94/Gate0B canary still requires the
owner to provision each host's dedicated SSH key pair, `known_hosts`,
`authorized_keys`, `sshd` subsystem, destination bootstrap receipt, native
publication receipt, and private profile receipt through the protected host
runbook. Shipyard will refuse an absent, stale, or mismatched prerequisite;
it never guesses or creates one. Capture the resulting `custody doctor`
receipt on both hosts and verify the two machine/incarnation/route bindings
before enabling a canary. This keeps the public default generic and prevents
an incomplete manual SSH setup from silently becoming custody authority.

Disabling the carrier is a configuration cutover, not history erasure. Pass
the exact policy digest printed by `doctor` or `provision`; dry-run verifies
the generation and `--apply` removes only that digest-matching
`[custody_transport]` table under the writer lease and atomic publication,
preserving unrelated machine configuration. The append-only custody ledger and
all terminal receipts remain intact. Active transport state is reconciled by
the normal ledger lifecycle before disabling; if any pending claim, transfer,
control, or successor rebind remains, the command refuses with no write. This
command never purges WAL history. SSH configuration, keys, and known-hosts
remain owner-managed and are never deleted by Shipyard.

```toml
[custody_transport]
enabled = true
setup_contract_version = 1
local_machine_ref = "machine_<64 lowercase hex>"
local_incarnation_ref = "incarnation_<64 lowercase hex>"
local_route_ref = "route_<64 lowercase hex>"
local_terminal_adapter = "cmux"
mutation_authority_machine_ref = "machine_<64 lowercase hex>"
authority_digest = "<64 lowercase hex>"
sender_owner_ref = "owner_<64 lowercase hex>"
inbox_owner_ref = "owner_<64 lowercase hex>"
sshd_config_file = "/etc/ssh/sshd_config"
authorized_keys_file = "/owner/private/shipyard/custody/authorized_keys"
lease_seconds = 30
deadline_seconds = 12
max_output_bytes = 262144

[[custody_transport.peers]]
machine_ref = "machine_<64 lowercase hex>"
incarnation_ref = "incarnation_<64 lowercase hex>"
route_ref = "route_<64 lowercase hex>"
terminal_adapter = "cmux"
ssh_program = "/usr/bin/ssh"
destination = "custody-peer"
known_hosts_file = "/owner/private/shipyard/custody/known_hosts"
identity_file = "/owner/private/shipyard/custody/id_ed25519"
outbound_identity_sha256 = "<sha256 of this host's outbound public key>"
inbound_public_key_file = "/owner/private/shipyard/custody/peer-id_ed25519.pub"
port = 22
remote_subsystem = "shipyard-custody-v1"
ssh_auth_key_sha256 = "<sha256 of peer's inbound exposed SSH public key>"
successor_proof_digest = "<64 lowercase hex>"
```

Paths and argv are fixed by protected policy. The carrier clears its
environment and disables ambient SSH config, agents, multiplexing, proxy/jump
commands, local commands, and forwarding. Known-host authority and the private
identity are opened without following symlinks and are checked for safe owner
and mode. No token, payload, or private key content appears in argv or errors.

## SSH receiver setup

Use one dedicated key per configured peer. Configure `sshd` with
`ExposeAuthInfo yes`, a dedicated subsystem, and a restricted key:

```text
Subsystem shipyard-custody-v1 /owner/private/bin/shipyard --mode shipyard work-ledger custody-receive
restrict ssh-ed25519 AAAA...
```

The SSH subsystem avoids a remote shell command entirely. The receiver hashes
the single public key recorded by `SSH_USER_AUTH` and matches it uniquely to the
peer policy before parsing or mutating the ledger. Exactly one
configured machine is the mutation authority. Other machines fail closed for
transfer, successor-rebind, correction, and revocation mutations.

## Incarnation replacement and offline rejoin

An accepted but unprocessed item can move only through an authenticated
successor rebind. The record binds the old and new process incarnations,
monotonic authority epoch, message/payload/workstream identity, old custody
receipt, new route, and successor proof. The destination commits the successor
custody before the source acknowledges it. Replays are idempotent; a late old
daemon, a second consumer, processed item, or contradictory successor is
refused. The sender retains custody throughout and never redelivers a second
effect.

Routine reconciliation is a five-second, bounded, no-model daemon task. A
missing peer, timeout, malformed response, or one repository's bad record is
reported as a redacted daemon diagnostic and retried after restart or offline
rejoin; it does not disable ordinary Shipyard stewardship.

Native wakes are staged only on a non-authority host and are fenced out of its
local provider consumer once staged. The elected authority marks a received
obligation processed only after its disjoint local WAL contains the exact
authenticated native publication, wake generations, protected payload digest,
workstream handle, and revision. Custody never copies credentials or silently
constructs missing publication authority; an absent or contradictory local
publication remains received and retryable.

Enablement is an explicit custody cutover. A non-authority host refuses to
stage while any native wake is already `claimed` or `uncertain`; drain or
reconcile that original local provider custody before enabling this carrier.
